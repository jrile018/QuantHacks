# Skill use in QuantHaxs chats

Owner: Track work across project chats. This is a routing guide for the active chats, not a new implementation contract or evidence of runtime, model, or economic acceptance. Check for relevant skills on every prompt, then read only the instructions needed for that task. The human's current request, the live Codex tool schema, checkout ownership, and existing authorization take precedence over cached skill examples.

## Rules shared by every chat

- Keep one planning workflow for the task. Continue the owner's existing plan and progress files; do not create a second root plan. `task_plan.md` and `progress.md` at the repository root belong to Post Benchmark. Other lanes write only within their owned checkout and planning area.
- Use skills as methods. A map, skill checklist, passing test, owner report, or delivered message does not certify a consumer handoff, executable backtest, Sharpe estimate, profit, or deployment. Record **delivered**, **acknowledged**, **consumer observed**, and **accepted** separately, with source version and receipt.
- Preserve exact negative results, failed runs, missingness, source quarantine, unknown clocks, and unresolved gates when compressing context. Point to authoritative files and hashes instead of pasting entire histories. Recheck changed sources before reusing an old conclusion.
- Use the live collaboration tools and their current schema. Claude `Agent()` examples and `haiku`/`sonnet`/`opus` names are not Codex spawn arguments here. A focused read, search, or check can use `gpt-6-luna`; clear documentation, code, or review can use `gpt-6-sol`; architecture judgment stays with the current root model. Route a new scoped subagent within the four-slot limit for that agent tree; this is not a global limit on app chats. Full-history forks inherit their model and effort and do not accept overrides in this session. Do not change another user chat's model or thinking setting unless the human requests it. Creating or messaging a user chat requires its own human authorization; model-routing advice never supplies that authority.
- Savings percentages and prices in router skills are illustrative and unverified for these chats. Do not report measured savings or edit global model, thinking, plugin, or telemetry settings from them.
- Keep the existing remote-compute rule even though no local `remote-compute` skill was found: large backtests, full suites, large data, and training run on `home-pc` through Tailscale in detached `tmux`, with logged exit status. Respect the shared heavy-job lock and the current two-thread, 4 GiB bound; keep bulk data remote and retrieve bounded results. Do not substitute a LAN address. Paid data, numerical risk/instrument decisions, protected final test, and other human gates remain in force. An optional global graph rebuild, full suite, or full Monte Carlo run must not delay the first small validated, realistic-cost milestone.
- `grill-me` was not found as a locally installed skill. The previously documented public-source grill method is a manual fallback, not an installed capability or new authorization. Cached Planning with Files, UI, and Obsidian definitions likewise do not prove native exposure in this session. Use connectors, design skills, and marketing skills only when the task actually calls for them.

## Pick the smallest useful method

| Task trigger | Skill or method | QuantHaxs use and limit |
|---|---|---|
| Locate code or understand a symbol | `claude-mem:smart-explore` when its `smart_search`, `smart_outline`, and `smart_unfold` MCP tools are available; otherwise scoped `rg` and source reads | Search the named checkout and inspect guards and consumers. An AST outline is navigation, not proof that code ran. |
| Recover prior-session context | `claude-mem:mem-search` | Search IDs, inspect timeline, then fetch only selected observations. Treat memory as a pointer to current files and receipts. |
| Design a new feature or major change | `superpowers:brainstorming`, then the one selected planning workflow | Resolve material choices before implementation; continue approved design without asking for duplicate approval. Keep each plan in its owner's area. |
| Implement an approved feature | `finishing-approved-work`; TDD or execution skill when it fits the change | Work within the approved slice and owned files. Use focused tests with meaningful failure cases; low-impact reversible documentation does not need mirror tests. |
| Diagnose a bug or failed boundary | `superpowers:systematic-debugging` | Preserve the original failure, test a cause, and separate an observed fix from an unrun hypothesis. |
| Validate or review | `superpowers:verification-before-completion`, focused code review, `auditing-project-truth` | Verify the exact claim with fresh evidence. Distinguish local code, remote merge state, runtime behavior, owner report, and economic acceptance. Run broader tests only for a concrete remaining risk or required gate. |
| Map architecture or impact | `icm-architect`; `gsd-graphify` only when its CLI and source freshness are verified | The existing graph is an archived source snapshot. Inspect current files for consequential claims; do not rebuild globally by default or treat a node as a live accepted interface. |
| Rank research paths or data sources | `ranking-evidence-backed-options`; quantitative research checks where relevant | State objective, hard gates, uncertainty, source quality, independent sample unit, costs, and falsification. A cached `quant-research` file can inform judgment but is not natively exposed here; its parameter-count heuristic is not an acceptance rule. |
| Explain a result or show it | `explaining-for-recall` for a requested teaching explanation; native `visualize` when interaction improves understanding | Use a small Markdown table or Mermaid for static structure. Use standard plotting tools for scientific/export figures. A visual never upgrades evidence. |

The cached `project-architecture` and `latex-math` files are not natively exposed in this session. Apply architecture principles through the existing contract and `icm-architect`; use LaTeX guidance only for an actual math-document deliverable. The cached Claude Planning with Files skill expects root planning files and Claude hooks, so it must not take over Post Benchmark's root files or replace an owner-specific workflow.
